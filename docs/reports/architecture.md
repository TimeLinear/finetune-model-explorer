# RAG 파이프라인 구조

> 개발 기간 2026-10-21~23. 측정값은 각 항목에 적은 날짜 기준이다.
> 기능 번호(F2001 등)는 [features.md](features.md)를 따른다.

## 1. 전체 흐름

```
[데이터 준비 — 앱 실행 전]
items_20261021.json ─▶ 모델 카드 수집(리비전 고정) ─▶ 소개 요약 생성(LLM) ─▶ 항목 색인 텍스트
                                     │                                         │
                                     ▼                                         ▼
                           카드 청킹 ─▶ docs 컬렉션                     items 컬렉션

[질문 시 — LangGraph]
질문 + 선택 모델
  └▶ retrieve 노드
       ├ items: 선택 모델 항목 청크 (항상 [근거 1], 다운로드 수 한 줄 덧붙임)
       ├ docs:  카드 색인 확인 (없으면 즉석 수집·색인)
       ├ 추가 문서: 프롬프트 1(검색어) → 위키 검색 → 프롬프트 2(선별) → 색인 (수집한 검색어는 건너뜀)
       └ docs에서 model_id 필터로 출처별 k개 검색 → 병합·중복 제거 → 근거 번호 부여
  └▶ generate 노드
       └ 프롬프트 3(근거 기반 답변) → [근거 n] 추출 → 인용된 근거만 표시
```

코드: 데이터 준비 `data_prep/`, 색인·검색 `vectorstore/`, 그래프 `rag/graph.py`, 근거 처리 `rag/evidence.py`, 서비스 기능 `services/`, 화면 `app.py`·`pages/`·`web/`.

## 2. 컬렉션 구조와 메타데이터

### 2.1 컬렉션 2개

| 컬렉션 | 내용 | 청크 단위 | 청크 ID |
|---|---|---|---|
| `items` | 모델 202개의 색인 텍스트 | 모델당 1개 | `item:{model_id}` |
| `docs` | 모델 카드 + 위키백과 문서 | 소제목 → 1,000자 분할 | `{model_id}:{doc_id}:{chunk_index}` |

모델 카드와 위키 문서를 한 컬렉션에 두고 `doc_type`으로 구분한다. 출처별 몫을 보장하려고 `doc_type` 필터 검색을 출처마다 따로 한다 (4절).

### 2.2 `items` 메타데이터
`model_id`, `params_b`, `stage`, `category`, `vendor_country`, `license`, `gated`, `context_len`, 모달리티 플래그(`mod_text`, `mod_image` …), 언어 플래그(`lang_ko`, `lang_en` …), `downloads_30d_adj`, `status`, `snapshot_date`, `source_type`, `card_url`, `card_revision`

- 목록 필드는 플래그로 펼친다 (Chroma 메타데이터 값 형식 제약). None은 키를 뺀다.

### 2.3 `docs` 메타데이터
| 필드 | 용도 |
|---|---|
| `model_id` | 검색 범위를 선택 모델로 좁힘 (빠지면 다른 모델 문서가 근거에 섞임) |
| `doc_type` | `model_card` / `wiki` — 출처 종류 표시 (F2016) |
| `doc_id`, `title`, `url`, `section` | 문서 식별, 근거 표시 |
| `doc_lang` | 문서 언어 (다국어 확장) |
| `revision` | 카드 커밋 해시 / 위키 리비전 — 재색인 판단 |
| `chunk_index`, `collected_at`, `search_query` | 순서, 관리, 재수집 방지 |

## 3. 문서 수집·청킹·색인 흐름

| 단계 | 모델 카드 (항목 자체 문서) | 위키백과 (추가 문서) |
|---|---|---|
| 수집 시점 | 앱 실행 전 일괄 + 미색인 모델은 질문 시 즉석 | 질문 시 |
| 선별 | 없음 (항상 색인, F2004) | 프롬프트 2로 제목·요약 보고 선별 |
| 고정 | 카드 리비전(커밋 해시)으로 받음 | 위키 리비전 ID 기록 |
| 청킹 | 마크다운 소제목 단위 → 1,000자/중복 200자 | 1,000자/중복 200자 |
| 재색인 | 같은 리비전이면 건너뜀. 바뀌면 해당 문서 기존 청크 삭제 후 추가 | 같은 검색어면 건너뜀 (선별 0건이고 선별 모델·프롬프트 버전이 바뀌었으면 다시 선별, 9.2) |

색인 상태는 모델별로 기록한다 (`pending` / `indexing` / `done` / `failed`). 이후에는 배경 작업자 + 우선순위 큐로 확장할 계획이다 (질문이 들어온 모델을 최우선 처리).

## 4. 검색 결과 병합과 중복 제거

기준: [collections.md](../design/collections.md) 3·4절, [retrieval-and-ui.md](../design/retrieval-and-ui.md)의 검색 설정 (2026-10-22 갱신).

1. `items`에서 선택 모델 청크 1개를 검색 없이 가져와 [근거 1]로 둔다 (`retrieve.item_always`). 끝에 "최근 30일 다운로드" 한 줄을 메타데이터에서 덧붙인다.
2. `docs`는 **출처별로 따로** 검색한다. 둘 다 `model_id = 선택 모델` 필터를 건다.
   - 모델 카드 (`doc_type=model_card`): P1이 만든 영어 검색 문구 `card_query_en`으로 `retrieve.card_k`(6)개 (2026-10-23에 4 → 6, 9.2 참고). 카드 청크에는 본문 청크와 **머리말 조각**(`section="front_matter"`, `card.front_matter_keys`에 정한 키만 "키: 값" 텍스트로 바꾼 것)이 함께 들어 있다. 가치가 낮은 소제목(`chunk.exclude_sections`: Citation, BibTeX, Contributors, Acknowledgement, Table of Contents, Contact)의 청크는 색인 단계에서 빠져 검색 대상이 아니다.
   - 위키백과 (`doc_type=wiki`): 원래 질문으로 `retrieve.wiki_k`(2)개.
   - `retrieve.search_type=mmr`이면 출처별로 `retrieve.mmr_fetch_k`(30)개 후보에서 `card_k`/`wiki_k`개를 MMR로 고른다 (F2014. 기본값은 `similarity`).
   - 따로 검색하는 이유: 한 컬렉션에서 함께 검색하면 한국어 질문이 한국어 위키 청크에 끌려 영어 카드 청크가 근거에서 모두 빠지는 현상이 확인됐다 (9.2).
3. 항목 → 카드 → 위키 순으로 합치고, 청크 ID 기준으로 중복을 제거한 뒤 순서대로 번호를 붙인다. 위키 청크가 모자라도 카드로 채우지 않는다.
4. 근거 블록마다 출처 종류·제목·섹션을 머리에 붙여 LLM에 넘긴다.
5. 색인 규칙(머리말·섹션 제외·청크 설정)이 바뀌면 `index.version`을 올린다 (현재 2). 색인 상태 기록의 건너뛰기 기준은 `model_id` + `card_revision` + `index_version`이다.

## 5. 프롬프트

모델은 `config/llm.json`의 작업 키로 정한다. 현재 프로필 `anthropic_direct`(Anthropic API 직접 호출): `LLM_SMALL` = claude-haiku-5-5, `LLM_ANSWER` = claude-haiku-5-5, `LLM_SUMMARY` = claude-sonnet-5-5. 초기 개발 단계의 API 프록시를 쓰던 2026-10-23까지는 `LLM_SMALL`이 gpt-5.4-nano였다 (나머지 둘은 같음).

| 프롬프트 | 역할 | 출력 형식 | 작업 키 |
|---|---|---|---|
| 1. 검색어 추출 | 카드 검색 영어 문구 `card_query_en` + 카드 밖 배경 문서용 위키 검색어 0~3개. 첫 검색어는 모델 계열명 | 구조화 출력 `queries[{query, reason}]` | `LLM_SMALL` |
| 2. 후보 선별 | 위키 후보(제목·요약)에서 근거로 쓸 문서 선택 | 구조화 출력 `decisions[{index, selected, reason}]` | `LLM_SMALL` |
| 3. 답변 생성 | 근거만 사용, 문장마다 `[근거 n]`, 없으면 "확인되지 않습니다" | 마크다운 텍스트 | `LLM_ANSWER` |
| (조건 변환) | 자연어 조건 → 필터·정렬·의미 검색어 | 구조화 출력 | `LLM_SMALL` |
| (조건 선별) | 후보 중 조건에 맞는 모델만, 후보 순서대로 최대 개수까지 + 이유 (v0.4, 2026-10-23. 이전에는 후보마다 `match`) | 구조화 출력 `picks[{model_id, reason}]`. 코드에서 후보에 없는 ID 제거·중복 제거·후보 순서 정렬·최대 개수 자르기 | `LLM_SMALL` |
| (점검표) | 사용 조건 7개 항목을 근거와 함께 정리 | 구조화 출력 | `LLM_ANSWER` |
| (소개 요약) | 카드 → 한국어 2~3문장 요약 (데이터 준비) | 구조화 출력 | `LLM_SUMMARY` |

**설계 방침**
- "도메인 전문가 역할"은 빈 페르소나가 아니라 구체적 작업 맥락으로 쓴다.
- 구조화 출력은 API 차원에서 강제한다 (`with_structured_output`). 방식은 모델 이름별로 `structured_output_method`에서 정한다 (claude-sonnet-5-5는 `json_schema`, 나머지는 `function_calling`).
- 구조화 출력이 출력 상한에서 잘리면(Anthropic `stop_reason="max_tokens"`, OpenAI 호환 `finish_reason="length"`) 파싱 결과를 쓰지 않고 실패로 처리한다 (`common/llm.py` `check_truncated`). 화면에는 짧은 오류 안내, `logs/app.log`에는 프롬프트 이름·모델·출력 토큰을 남긴다. 요약(S)은 잘리면 재시도하지 않는다.
- 근거는 번호·출처 종류가 붙은 블록으로 넣는다 (근거 번호 인용 정확도).
- 선별 프롬프트는 선택·제외 이유를 받는다 ([evaluation.md](evaluation.md)의 문서 수집 검증에 사용).
- few-shot 예시는 가상 모델명만 쓴다 (예시 내용을 베껴 답하는 위험 방지).

원문: `prompts/ko/`, 설계: [prompts.md](../design/prompts.md), 모델 선택: [models.md](../design/models.md)

## 6. 청크 크기·중복·근거 수

| 설정 | 값 | 이유 | 바꿨을 때의 차이 |
|---|---|---|---|
| 청크 크기 | 1,000자 | 흔히 쓰는 출발값. 모델 카드는 소제목 단위로 먼저 나눠 주제가 섞이지 않게 함 | 1,000자/200자에서 카드 202개 → 4,667청크(모델당 최대 99). 같은 카드 3개(kanana·gemma-3-4b-it·Mamba-Codestral) 기준 1,000자/200자 60청크 → 500자/100자 99청크 (2026-10-22 측정). 답변 품질 차이는 아직 비교하지 않음 |
| 중복 | 200자 | 문단 경계에서 문맥이 끊기는 것 방지 | 청크 크기와 함께 500자/100자로 바꿔 측정한 결과만 있음(위 행). 중복만 바꾼 비교는 아직 하지 않음 |
| 근거 수 | 항목 1 + 카드 6 + 위키 2 (2026-10-23 전까지 카드 4) | 선택 모델 범위 안에서만 검색하므로 후보가 수십 개 수준. 카드 4개일 때 정답 조각이 5~6위에 걸려 빠지는 경우가 있어 6으로 늘림: 평가 세트 검색 적중 90/99 → 96/99, 답변 정답 31/33 → 33/33, 입력 토큰 중앙값 +26% (9.2) | 출처별 분리 검색 후(2026-10-22 측정), kanana, "이 모델의 라이선스 조건은?": 카드 4·위키 2 → 근거 7개(항목 1·카드 청크 6·9·2·3·위키 청크 21·14), 카드 2·위키 1 → 근거 4개(항목 1·카드 6·9·위키 21). 앞쪽 청크는 같고 뒤쪽이 빠짐. (분리 전 통합 검색 `docs_k` 측정: 문서 5 → 근거 6개, 문서 3 → 근거 4개) |
| 검색 방식 | 유사도 (확장: MMR — 출처별 fetch 30 → card_k / wiki_k) | 카드 안에서 비슷한 문단이 몰리는 경우 MMR로 다양성 확보 | 출처별 분리 검색 후(2026-10-22 측정), 같은 질문, 카드 4·위키 2: 유사도 → 카드 6·9·2·3 + 위키 21·14, MMR(fetch 30, λ 0.5) → 카드 6·9·7·10 + 위키 21·23. 카드에서는 목차(2)·Kanana 1.5 소개(3) 대신 Processing 32K+ Length(7)·Contact(10)가, 위키에서는 다른 절(각주)이 들어옴. (분리 전 통합 검색 측정: 유사도 카드 0·1·6·4 + 위키 21, MMR 카드 0·6·8 + 위키 21·11) |

모든 값은 `config/settings.json`에서 바꿔 비교한다.

## 7. 근거 표시 방식

- 답변 본문의 `[근거 n]` 표기를 정규식으로 찾아, 실제 인용된 번호의 근거만 화면에 남긴다 (`rag/evidence.py`).
- 근거마다 출처 종류(항목 메타데이터 / 모델 카드 / 위키백과), 제목, 섹션, 원문 링크를 표시한다.
- 인용된 근거가 하나도 없으면 "이 답변에는 인용된 근거가 없습니다."를 표시한다.

## 8. 도메인 특화 기능 설계 이유 — 사용 조건 점검표

- 파인튜닝할 모델을 회사에서 고를 때 가장 먼저 막히는 것은 성능보다 **사용 조건**(라이선스, 승인 절차, 언어, 컨텍스트, 입력 형식)이다.
- 이 정보는 모델마다 다르고 카드 여기저기에 흩어져 있으며, 근거 없이 답하면 위험하다 → RAG가 가장 필요한 지점이다.
- 점검표 형태로 항목을 고정하면 "카드에 없음"도 명시적으로 드러나 사용자가 무엇을 추가 확인해야 하는지 알 수 있다.
- 라이선스는 조건 전달만 하고 가부 판단은 하지 않으며, 면책 문구를 함께 표시한다.

## 9. 선택 이유, 겪은 문제와 해결

### 9.1 데이터 준비 단계 (2026-10-21~22)

| 문제 | 원인 | 해결 |
|---|---|---|
| 처음 고른 데이터셋(Epoch AI)에 중간 규모 오픈 모델이 부족 | 프런티어·역사적 모델 중심 데이터셋 | Hugging Face Hub API로 출처 변경, 공식 조직 계정만 수집 |
| 같은 모델이 형식만 다른 저장소로 중복 | BF16 별도 저장소, -HF 변환본 | 이름 규칙으로 중복본 제외 |
| 특수 목적 모델이 범용 모델과의 다운로드 경쟁에서 탈락 | 이용자층 크기 차이 | 그룹(범용·분야·우선 지역) 내 상대 순위로 선별 |
| 게이트 모델(Llama·Gemma 등 35개)의 설정 파일 조회 실패 | 라이선스 동의 필요, Meta는 세대별 약관 | 저장소별 동의 후 토큰으로 조회 |
| 일부 설정 파일 다운로드 실패 | 대용량 저장 방식(LFS)으로 저장돼 CDN(`*.hf.co`)으로 넘겨짐 | 네트워크 허용 목록에 CDN 도메인 추가 |
