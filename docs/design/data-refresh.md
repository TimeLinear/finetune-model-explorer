# 데이터 갱신 설계

- 상태: 확정
- 최종 수정일: 2026-10-25
- 관련 문서: [backlog.md](backlog.md), [decisions.md](decisions.md), [evaluation.md](../reports/evaluation.md), [collections.md](collections.md)

## 요약

- 갱신 절차는 하나(`refresh`)이고 입구는 수동(명령·화면 버튼)과 자동(예약 실행, 기본 주 1회) 두 개다. 설정 `refresh.auto` 기본값은 `false`(수동).
- 카드 본문 해시가 바뀐 모델만 다시 수집·요약·색인하고, 새 색인은 별도 폴더에 만든다. 갱신 중에도 서비스는 기존 색인으로 동작한다.
- 목록은 그룹 내 최근 30일 다운로드 순위로 진입·퇴출을 정하고(진입·퇴출 기준을 다르게), 퇴출은 삭제가 아니라 보관이다.
- 평가 세트를 다시 돌려 검색 품질 하락(C 유형)이 4건 이상이거나 한 모델의 사례가 절반 넘게 나빠지면 새 색인으로 교체하지 않는다.
- 비용이 드는 단계는 소개 요약뿐이며 배치 API로 만들고, 갱신 1회 비용 상한(`refresh.max_cost_usd`)을 둔다.

> 상태: 설계 확정 (2026-10-25), 구현 전. 표의 수치는 잠정값이며 실제로 운용하면서 조정한다.

## 1. 목표

- 모델 목록(현재 2026-10-21 기준 202개)과 모델 카드·소개 요약·색인을 주기적으로 최신 상태로 유지한다.
- 갱신이 검색 품질을 깨뜨리지 않았는지 평가로 확인하고, 나빠졌으면 새 색인으로 교체하지 않는다.

## 2. 실행 경로

- 갱신 절차는 하나(`refresh`)이고, 입구가 두 개다.
  - **수동:** 명령(스크립트) 또는 화면의 갱신 버튼
  - **자동:** 예약 실행 (기본 주 1회)
- 설정 `refresh.auto`로 켜고 끈다. 기본값은 `false`(수동).
- 수동 경로를 먼저 구현하고, 자동은 그 위에 얹는다. 자동에 추가로 필요한 것: 동시 실행 잠금, 실패 기록·알림, 갱신 1회 비용 상한.
- 주기를 주 1회로 둔 이유: 최근 30일 누적 다운로드는 하루 사이에 크게 변하지 않아 매일 갱신하면 순위만 출렁인다. 급한 모델은 수동 경로로 갱신한다.

## 3. 절차

1. **조회:** Hugging Face API로 공식 조직의 모델 목록, 최근 30일 다운로드 수, 커밋 해시를 받는다. 카드 본문은 받지 않는다.
2. **목록 판정:** 4절 기준으로 진입·퇴출(보관)을 정한다.
3. **변경 판단:** 카드 본문 해시가 바뀐 모델만 처리 대상으로 삼는다. 커밋 해시만 바뀐 경우(가중치 파일 변경 등)는 메타데이터만 갱신한다.
4. **수집·요약:** 대상 모델의 카드를 받고 소개 요약을 다시 만든다 (배치 API).
5. **색인:** 새 색인을 별도 폴더에 만든다. 기존 색인을 복사한 뒤 대상 모델의 청크만 카드 전체 단위로 교체한다.
6. **점검·평가:** 5절.
7. **교체 판정:** 6절. 통과하면 새 색인으로 전환한다. 갱신 중에도 서비스는 기존 색인으로 동작한다.
8. **보고서 저장:** 7절.

## 4. 목록 기준 (잠정)

지표는 **최근 30일 다운로드 수의 그룹 내 순위**다. 다운로드 절대값은 시기마다 규모가 달라 순위를 쓴다.

| 항목 | 의미 | 값 |
|---|---|---|
| 진입 순위 | 그룹 안에서 이 순위 안이면 목록에 들어온다 | 현재 그룹별 정원 |
| 퇴출 순위 | 이 순위 밖으로 밀려나야 퇴출 후보가 된다 | 그룹별 정원의 1.5배 |
| 연속 횟수 | 퇴출 후보 상태가 이만큼 연속돼야 보관한다 | 2회 (주 1회 갱신 기준 약 2주) |
| 보호 기간 | 최근 이 기간 안에 질문받은 모델은 퇴출하지 않는다 | 30일 |
| 신규 유예 | 공개 후 이 기간 안의 모델은 퇴출 판정에서 뺀다 (30일 누적이 작아서) | 공개 후 30일 |

- 진입과 퇴출 기준을 다르게 두는 이유: 경계에 있는 모델이 갱신 때마다 들어왔다 나갔다 하는 것을 막는다.
- 퇴출은 삭제가 아니라 보관(`status=archived`)이다. 기본 목록에서 숨기고 검색으로는 찾을 수 있다. 색인은 유지한다.
- 보호 기간 판정을 위해 모델별 마지막 질문 일시를 기록한다.

## 5. 점검과 평가

### 평가 세트 정답 다시 연결

- 평가 세트의 정답은 청크 ID에 묶여 있다. 카드가 바뀐 모델은 저장된 **정답 근거 문장**이 들어 있는 새 청크를 찾아 정답을 다시 연결한다.
- 그다음 평가 세트를 다시 실행한다. 저장된 검색 문구를 쓰므로 LLM 호출이 없고 결과가 실행마다 같다.

### 나빠진 사례의 유형

| 유형 | 의미 | 대응 |
|---|---|---|
| A. 정답을 다시 못 찾음 | 근거 문장이 새 카드에서 쪼개지거나 표현이 바뀜 | 평가 데이터 문제. "검토 필요"로 표시하고 판정 집계에서 뺀다 |
| B. 사실 자체가 바뀜 | 카드 내용이 실제로 바뀌어 기존 정답이 맞지 않음 (예: 라이선스 변경) | "폐기 후보"로 표시하고 보고서에 바뀐 내용을 강조한다 |
| C. 검색 품질 하락 | 정답 문장은 그대로인데 순위가 밀려 놓침 | 실제 성능 저하. 6절 교체 판정에 쓴다 |

### 평가 세트가 다루지 않는 모델 점검 (LLM 호출 없음)

카드가 바뀐 모든 모델에 대해:
- **중요 필드 변경:** 라이선스, 승인 필요 여부, 컨텍스트 길이가 바뀌면 보고서 맨 위에 표시한다.
- **청크 수 급변:** 절반 이하로 줄거나 두 배 이상 늘면 표시한다 (카드 대폭 변경 또는 파싱 오류 신호).
- **머리말 누락:** 전에 있던 머리말(라이선스·이용 조건) 청크가 사라지면 표시한다.

## 6. 교체 판정 (잠정)

| 단계 | 조건 | 대응 |
|---|---|---|
| 정상 | C 유형 0건 | 새 색인으로 교체, 보고서 기록 |
| 경미 | C 유형이 평가 질의 99개 중 3건 이하 | 교체하고 해당 사례를 "확인 필요"로 보고 |
| 심각 | C 유형 4건 이상, 또는 한 모델의 사례가 절반 넘게 나빠짐 | **교체하지 않는다.** 기존 색인으로 계속 서비스하고 원인 확인 후 수동으로 결정 |

- 평가 세트 수명: "검토 필요"와 "폐기 후보"가 전체 사례의 20%를 넘으면 평가 세트를 다시 작성할 시점으로 보고 알린다.
- 평가 세트에 든 모델이 보관 상태가 되어도 색인은 남으므로 평가는 계속 돌아간다.

## 7. 데이터 파일

| 파일 | 내용 |
|---|---|
| `data/items.json` | 앱이 읽는 현재 목록. 이름은 바뀌지 않는다 |
| `data/refresh/YYYY-MM-DD.json` | 갱신 보고서: 추가·보관 모델, 카드 변경 모델, 중요 필드 변경, 점검 결과, 평가 결과, 교체 여부, 소비 토큰·비용 |

- 날짜는 ISO 형식(`2026-10-25`)을 쓴다.
- 과거 목록 전체는 git 이력으로 남기고, 날짜별 전체 사본은 두지 않는다.
- 기존 `data/items_20261021.json`은 첫 기준본이다. 갱신 기능을 도입할 때 `data/items.json`으로 옮긴다.
- 배포 서버에서 자동 갱신이 돌 때의 이력 보관 방식은 배포 단계에서 정한다.

## 8. 비용

- 비용이 드는 단계는 **소개 요약(LLM)뿐**이다. 조회, 카드 다운로드, 임베딩·색인, 평가, 점검은 로컬 작업이거나 무료 API다.
- 요약 1개: 입력 약 6,500 · 출력 약 450 토큰. Sonnet 5.5 기준 약 $0.018, 배치 API 약 $0.009.
- 주 20~40개 모델의 카드가 바뀐다고 보면 배치 API 기준 월 $0.8~1.5.
- 원칙:
  - 요약은 카드 본문이 바뀐 경우에만 다시 만든다.
  - 갱신용 요약은 배치 API로 만든다 (갱신은 시간이 급하지 않은 작업).
  - 갱신 1회 비용 상한을 설정(`refresh.max_cost_usd`)으로 두고, 넘을 것 같으면 요약을 멈추고 보고한다.
