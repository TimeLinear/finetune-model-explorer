# 데이터 갱신 설계

- 상태: 확정
- 최종 수정일: 2026-10-25
- 관련 문서: [backlog.md](backlog.md), [decisions.md](decisions.md), [evaluation.md](../reports/evaluation.md), [collections.md](collections.md)

## 요약

- 갱신 절차는 하나(`refresh`)이고 입구는 수동(명령·화면 버튼)과 자동(예약 실행, 기본 주 1회) 두 개다. 설정 `refresh.auto` 기본값은 `false`(수동).
- 카드 본문 해시가 바뀐 모델만 다시 수집·요약·색인하고, 새 색인은 별도 폴더에 만든다. 갱신 중에도 서비스는 기존 색인으로 동작하고, 교체할 때 직전 색인 한 세대를 남겨 한 명령으로 되돌린다.
- 목록은 그룹 내 최근 30일 다운로드 순위로 진입·퇴출을 정하고(진입·퇴출 기준을 다르게), 퇴출은 삭제가 아니라 보관이다.
- 평가 세트를 다시 돌려 검색 품질 하락(C 유형)이 4건 이상이거나 한 모델의 사례가 절반 넘게 나빠지면 새 색인으로 교체하지 않는다.
- 비용이 드는 단계는 소개 요약뿐이다. 지금 규모(주 수 개)에서는 일반 API로 만들고, 대상이 많아지면 배치 API로 바꾼다. 갱신 1회 비용 상한(`refresh.max_cost_usd`)을 둔다.
- 목록이 한 번에 크게 바뀌면(활성 목록의 20% 초과) 반영하지 않고 사람이 확인한다. 대량 변화 대응은 9절.

> 상태: 설계 확정 (2026-10-25). 1단계(조회·판정 시험 실행) 구현 완료, 2단계(수동 반영) 구현 중. 표의 수치는 잠정값이며 실제로 운용하면서 조정한다.

## 1. 목표

- 모델 목록(현재 2026-10-21 기준 202개)과 모델 카드·소개 요약·색인을 주기적으로 최신 상태로 유지한다.
- 갱신이 검색 품질을 깨뜨리지 않았는지 평가로 확인하고, 나빠졌으면 새 색인으로 교체하지 않는다.

## 2. 실행 경로

- 갱신 절차는 하나(`refresh`)이고, 입구가 두 개다.
  - **수동:** 명령(스크립트) 또는 화면의 갱신 버튼
  - **자동:** 예약 실행 (기본 주 1회)
- 설정 `refresh.auto`로 켜고 끈다. 기본값은 `false`(수동).
- 수동 경로를 먼저 구현하고, 자동은 그 위에 얹는다. 자동에 추가로 필요한 것: 동시 실행 잠금, 실패 기록·알림, 갱신 1회 비용 상한.
- 주기를 주 1회로 둔 이유: 최근 30일 누적 다운로드는 하루 사이에 크게 변하지 않아 매일 갱신하면 순위만 출렁인다. 급한 모델은 수동 경로로 갱신한다.

## 3. 절차

1. **조회:** Hugging Face API로 공식 조직의 모델 목록, 최근 30일 다운로드 수, 커밋 해시를 받는다. 카드 본문은 받지 않는다.
2. **목록 판정:** 4절 기준으로 진입·퇴출(보관)을 정한다.
3. **변경 판단:** 카드 본문 해시가 바뀐 모델만 처리 대상으로 삼는다. 커밋 해시만 바뀐 경우(가중치 파일 변경 등)는 메타데이터만 갱신한다.
4. **수집·요약:** 대상 모델의 카드를 받고 소개 요약을 다시 만든다 (일반 API. 대상이 많으면 배치 API, 9절).
5. **색인:** 새 색인을 별도 폴더에 만든다. 기존 색인을 복사한 뒤 대상 모델의 청크만 카드 전체 단위로 교체한다.
6. **점검·평가:** 5절.
7. **교체 판정:** 6절. 통과하면 새 색인으로 전환한다. 갱신 중에도 서비스는 기존 색인으로 동작한다.
8. **보고서 저장:** 7절.

## 4. 목록 기준 (잠정)

지표는 **최근 30일 다운로드 수의 그룹 내 순위**다. 다운로드 절대값은 시기마다 규모가 달라 순위를 쓴다.

| 항목 | 의미 | 값 |
|---|---|---|
| 진입 순위 | 그룹 안에서 이 순위 안이면 목록에 들어온다 | 현재 선별 규칙의 그룹별 선발 수 k (그룹 크기 × 비율: 범용 18%, 우선 지역 50%, 특수 분야 30%·최소 2개) |
| 퇴출 순위 | 이 순위 밖으로 밀려나야 퇴출 후보가 된다 | k의 1.5배 (올림) |
| 연속 횟수 | 퇴출 후보 상태가 이만큼 연속돼야 보관한다 | 2회 (주 1회 갱신 기준 약 2주) |
| 보호 기간 | 최근 이 기간 안에 질문받은 모델은 퇴출하지 않는다 | 30일 |
| 신규 유예 | 공개 후 이 기간 안의 모델은 퇴출 판정에서 뺀다 (30일 누적이 작아서) | 공개 후 30일 |

- 진입과 퇴출 기준을 다르게 두는 이유: 경계에 있는 모델이 갱신 때마다 들어왔다 나갔다 하는 것을 막는다.
- 퇴출은 삭제가 아니라 보관(`status=archived`)이다. 기본 목록에서 숨기고 검색으로는 찾을 수 있다. 색인은 유지한다.
- 보호 기간 판정을 위해 모델별 마지막 질문 일시를 기록한다.
- 퇴출 순위 안쪽(진입 순위와 퇴출 순위 사이 포함)이면 연속 횟수를 0으로 되돌린다.
- 조회 결과에 아예 없는 모델(삭제·비공개 전환·크기 범위 이탈 등)도 퇴출 후보로 본다. 보고서에 사유를 남긴다.
- 보관된 모델이 다시 진입 순위 안에 들면 활성으로 되돌린다.
- 공개 30일 미만 모델의 다운로드는 기존 선별 규칙대로 30일 기준으로 환산한 값을 쓴다 (신규 유예와 별개).

## 5. 점검과 평가

### 평가 세트 정답 다시 연결

- 평가 세트의 정답은 청크 ID에 묶여 있다. 카드가 바뀐 모델은 저장된 **정답 근거 문장**이 들어 있는 새 청크를 찾아 정답을 다시 연결한다.
- 사례의 근거 문장 중 일부만 찾으면 찾은 청크로 다시 연결하고, 못 찾은 문장은 보고서에 남긴다. 하나도 못 찾을 때만 A 유형이다.
- 그다음 평가 세트를 다시 실행한다. 저장된 검색 문구를 쓰므로 LLM 호출이 없고 결과가 실행마다 같다.

### 나빠진 사례의 유형

| 유형 | 의미 | 대응 |
|---|---|---|
| A. 정답을 다시 못 찾음 | 근거 문장이 새 카드에서 쪼개지거나 표현이 바뀜 | 평가 데이터 문제. "검토 필요"로 표시하고 판정 집계에서 뺀다 |
| B. 사실 자체가 바뀜 | 카드 내용이 실제로 바뀌어 기존 정답이 맞지 않음 (예: 라이선스 변경) | "폐기 후보"로 표시하고 보고서에 바뀐 내용을 강조한다 |
| C. 검색 품질 하락 | 정답 문장은 그대로인데 순위가 밀려 놓침 | 실제 성능 저하. 6절 교체 판정에 쓴다 |

### 평가 세트가 다루지 않는 모델 점검 (LLM 호출 없음)

카드가 바뀐 모든 모델에 대해:
- **중요 필드 변경:** 라이선스, 승인 필요 여부, 컨텍스트 길이가 바뀌면 보고서 맨 위에 표시한다.
- **청크 수 급변:** 절반 이하로 줄거나 두 배 이상 늘면 표시한다 (카드 대폭 변경 또는 파싱 오류 신호).
- **머리말 누락:** 전에 있던 머리말(라이선스·이용 조건) 청크가 사라지면 표시한다.

## 6. 교체 판정 (잠정)

| 단계 | 조건 | 대응 |
|---|---|---|
| 정상 | C 유형 0건 | 새 색인으로 교체, 보고서 기록 |
| 경미 | C 유형이 평가 질의 99개 중 3건 이하 | 교체하고 해당 사례를 "확인 필요"로 보고 |
| 심각 | C 유형 4건 이상, 또는 한 모델의 사례가 절반 넘게 나빠짐 | **교체하지 않는다.** 기존 색인으로 계속 서비스하고 원인 확인 후 수동으로 결정 |

- "한 모델의 사례"는 평가 질의(표현) 단위로 센다. 표의 다른 행이 99개 질의 기준이므로 단위를 맞춘다.
- 평가 세트 수명: "검토 필요"와 "폐기 후보"가 전체 사례의 20%를 넘으면 평가 세트를 다시 작성할 시점으로 보고 알린다.
- 평가 세트에 든 모델이 보관 상태가 되어도 색인은 남으므로 평가는 계속 돌아간다.

### 교체와 되돌리기

- 갱신은 작업 공간에서 새 목록·카드·매니페스트·요약·색인을 만든다. 서비스가 읽는 파일은 교체 전까지 바꾸지 않는다.
- 교체는 이 다섯 가지를 한 묶음으로 바꾼다. 모델 하나 안에서도 카드·요약·색인은 전부 반영하거나 전부 다음 회차로 넘긴다.
- 직전 묶음 한 세대를 보관한다. 되돌리기 명령은 현재와 직전을 맞바꾸므로 되돌리기도 다시 되돌릴 수 있다. 색인이 약 90MB라 한 세대 보관 부담은 작다.
- 앱이 색인을 연 상태에서 교체하면 꼬일 수 있으므로, 수동 갱신의 교체 단계는 앱이 꺼져 있을 때만 실행한다. 앱이 켜진 채로 교체하는 방법은 자동 갱신 단계에서 정한다.

## 7. 데이터 파일

| 파일 | 내용 |
|---|---|
| `data/items.json` | 앱이 읽는 현재 목록. 이름은 바뀌지 않는다 |
| `data/refresh/YYYY-MM-DD.json` | 갱신 보고서: 추가·보관 모델, 카드 변경 모델, 중요 필드 변경, 점검 결과, 평가 결과, 교체 여부, 소비 토큰·비용 |

- 날짜는 ISO 형식(`2026-10-25`)을 쓴다.
- 과거 목록 전체는 git 이력으로 남기고, 날짜별 전체 사본은 두지 않는다.
- 첫 기준본(2026-10-21 스냅샷 202개)은 갱신 1단계 도입 때 `data/items.json`으로 이름을 바꿨다 (2026-10-25). 이전 이름은 git 이력에 남아 있다.
- 배포 서버에서 자동 갱신이 돌 때의 이력 보관 방식은 배포 단계에서 정한다.

## 8. 비용

- 비용이 드는 단계는 **소개 요약(LLM)뿐**이다. 조회, 카드 다운로드, 임베딩·색인, 평가, 점검은 로컬 작업이거나 무료 API다.
- 요약 1개: 입력 약 6,500 · 출력 약 450 토큰. Sonnet 5.5 기준 약 $0.018, 배치 API 약 $0.009.
- 1단계 시험 실행(2026-10-25)의 실제 대상은 4개(신규 3, 카드 변경 1), 예상 비용은 일반 $0.072 / 배치 $0.036이었다. 주 20~40개로 늘어도 일반 API 기준 회당 $0.4~0.7 정도다.
- 원칙:
  - 요약은 카드 본문이 바뀐 경우에만 다시 만든다.
  - 갱신용 요약은 일반 API로 만든다. 지금 규모에서는 배치가 아끼는 돈(회당 수 센트)보다 결과 대기·상태 저장·실패 처리 코드의 부담이 크다. 요약 대상이 `refresh.batch_threshold`(30개)를 넘으면 배치 API로 바꾼다 (9절).
  - 갱신 1회 비용 상한을 설정(`refresh.max_cost_usd`)으로 두고, 넘을 것 같으면 우선순위대로 상한까지만 반영하고 나머지는 다음 회차로 넘긴다 (9절).

## 9. 대량 변화 대응

Hugging Face의 순위 변화가 지금(주 수 개)보다 크게 늘어날 때를 대비한 계획이다. 원칙은 **서비스는 언제나 마지막으로 교체 판정을 통과한 색인으로 동작하고, 갱신이 실패하거나 멈춰도 서비스에 영향이 없는 것**이다.

| 상황 | 신호 | 대응 | 구현 시점 |
|---|---|---|---|
| 평소 | 요약 대상 30개 이하, 예상 비용이 상한 안 | 전부 반영 (일반 API) | 2단계 |
| 비용 초과 | 예상 비용이 `refresh.max_cost_usd` 초과 | 우선순위대로 상한까지 반영하고 나머지는 다음 회차로 넘김 | 2단계 |
| 급변 | 신규·퇴출 후보·보관 예정·재활성 모델 수가 활성 목록의 20%(`refresh.anomaly_ratio`) 초과 | 반영하지 않고 보고서만 쓴다. 사람이 원인을 확인한 뒤 수동으로 반영 | 2단계 |
| 대상 많음 | 요약 대상이 30개(`refresh.batch_threshold`) 초과 | 요약을 배치 API로 만든다 (비용 절반, 결과까지 수 분~수 시간) | 필요해질 때 (지금은 보고서 경고만) |
| 실제 대개편 | 급변이 데이터 이상이 아니라 실제 변화로 확인됨 | 계획된 전체 재구축: 요약 전체(200개 기준 일반 약 $3.6, 배치 약 $1.8), 색인 새로 만들기, 평가 세트 점검 | 필요해질 때 |
| 진동 | 같은 모델이 보관과 재활성을 되풀이 | 퇴출 배율·연속 횟수(4절)를 올린다 | 운용 기록을 보고 |
| 목록 비대 | 그룹 크기가 커져 선발 수 k와 목록이 계속 늘어남 | 비율을 낮추거나 그룹별 상한을 둔다 (규칙 버전을 올림) | 운용 기록을 보고 |

- **다음 회차로 넘기는 순서:** ① 이미 목록에 있는 모델의 카드 변경 (낡은 정보는 틀린 답으로 이어진다) ② 재활성 ③ 신규 진입 (그룹 순위가 높은 순). 넘긴 모델은 목록과 카드 리비전을 바꾸지 않으므로 다음 회차에 같은 판정으로 다시 잡힌다. 대기열을 따로 두지 않는다.
- **급변을 바로 반영하지 않는 이유:** 목록의 상당 부분이 한 번에 바뀌면 실제 변화보다 API 응답 형식이나 다운로드 집계 방식이 바뀐 데이터 이상을 먼저 의심해야 한다. 잘못 반영하면 멀쩡한 모델이 대거 보관된다.
- **평가 세트 침식:** 평가 세트 모델 6개 중 절반 이상이 보관되거나 카드가 바뀌면, 6절의 20% 기준과 별개로 평가 세트를 다시 작성할 시점으로 보고 알린다.
- 기준 수치(30개, 20%)는 잠정값이며 운용하면서 조정한다.
